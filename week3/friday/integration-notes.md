# Integration and Troubleshooting Notes

Here is how I resolved the four specific integration challenges during the provisioning script development:

### Challenge A: The Read-Only File System Conflict
When I applied `ProtectSystem=strict` to the systemd service files to improve the security score, it made the entire file system read-only. This immediately broke the application because it couldn't write to its log files. To fix this without compromising the strict protection, I added `ReadWritePaths=/opt/kijanikiosk/shared/logs` to the service file. This essentially pokes a targeted, safe hole in the read-only shield just for that specific directory.

### Challenge B: Monitoring Tool Access
The monitoring tool (running as the `kk-logs` user) needed to read the `health.json` file generated by the API, but I didn't want to change the file's primary owner or group, or open it up to the world. I solved this by using Access Control Lists (ACLs). I ran `setfacl -m u:kk-logs:r-- health.json`, which explicitly granted read-only access to just that specific user while keeping the baseline permissions strict (`640`).

### Challenge C: Logrotate vs. Systemd Isolation
Normally, `logrotate` needs to restart or reload a service after moving its log files. However, because the systemd services are heavily isolated (using `PrivateTmp=true` and other hardening flags), standard reload commands were failing or causing permission issues. I bypassed this by using the `copytruncate` directive in the logrotate config. This copies the log data to a new file and empties the original file in place, meaning the application never has to let go of the file handle and doesn't need to be restarted at all.

### Challenge D: Package Version Drift
Because the server was in a "dirty" state, it was possible that someone had manually installed a newer or conflicting version of Nginx or Node.js. If the script just ran `apt-get install`, it might fail or break due to package holds. To make it idempotent, I added a check using `dpkg-query` to see exactly what version was currently installed. If it didn't match the pinned variable, the script uses `apt-get install --allow-downgrades` to force the server into the exact state we specified, regardless of what was there before.
