# KijaniKiosk Capstone Reflection

## What I Got Wrong

My biggest technical mistake was planning to deploy Prometheus using raw Kubernetes YAML manifests without understanding how Custom Resource Definitions (CRDs) and the Prometheus Operator work. In my initial scope and architecture, I planned to use Prometheus for monitoring and tried to apply manifest files I found directly into Minikube. The cluster immediately rejected them with "resource does not exist" errors because standard Kubernetes does not natively recognize resources like `PrometheusRule` without the Operator installed first. At the same time, while wiring the Ingress for `kk-payments`, I used a `rewrite-target: /` annotation that stripped the `/payments` prefix off incoming requests, causing Express to return `Cannot POST /` because my `index.ts` initially only had a `/health` endpoint.

With what I know now, I would not waste hours fighting unconfigured CRD manifests when structured logs are already available. Pivoting to Option B, adding a POST endpoint in `index.ts` to handle requests and simulate traffic, and using Bash and Python scripts to parse structured `kubectl logs` for the 5% error rate SLO, taught me to match the monitoring tool to the scale of the environment. If I did need full Prometheus in the future, I would deploy it using Helm (`kube-prometheus-stack`) in a dedicated `monitoring` namespace rather than applying raw YAML files manually.

## The Most Important Thing I Learned

The single most important concept I learned was **Decoupled Configuration and Namespace Isolation**, which first appeared in **Week 8 (Kubernetes & Containerization)**.

When I first deployed `kk-payments` in Week 8, I worked entirely inside the `default` namespace and relied on a manually created `kijani-registry-credentials` secret to pull my image from Docker Hub. At the time, I thought getting pods to show `1/1 Running` meant the deployment was production-ready. Building the capstone completely changed how I think about software delivery when I had to deploy the exact same `deployment.yaml` manifest into an isolated `kijani-staging` namespace via Jenkins and connect it to the Serverless simulator on my host machine.

First, I realized that hardcoding or copying `kijani-registry-credentials` across namespaces in Ansible would expose personal credentials and break the pipeline for anyone else cloning the repo. Making the `salyani123/kk-payments` repository public and removing `imagePullSecrets` showed me that a pipeline must be reproducible out of the box. Second, realizing that a pod inside `kijani-staging` treats `localhost` as its own container, not my Fedora host—forced me to use Ansible ConfigMaps to inject `[http://host.minikube.internal:3000/receipts](http://host.minikube.internal:3000/receipts)` and `kk-payments-receipts-staging`. I learned that application code and Kubernetes manifests should never care which environment they are in; the pipeline's job is to inject the surrounding context dynamically.

## What a Second Pass Would Look Like

If I had two more weeks with my current project as a starting point, I would make three specific changes to improve automation and clean up local workarounds:

* **Move the Serverless Simulator into the Cluster with LocalStack:** Right now, the Serverless receipt chain (`receipt.generated` -> `receipt.processed` -> `notification.dispatched`) requires running `npx serverless offline start` in a separate host terminal and routing out of the cluster via `host.minikube.internal`. I would remove `serverless-offline` and deploy **LocalStack** as a pod inside Minikube so the S3 buckets and Lambda triggers run entirely inside the Kubernetes network and start up automatically during the Jenkins run.
* **Automate the SLO Log Scripts as a Kubernetes CronJob or Pipeline Stage:** Currently, my Bash and Python monitoring scripts run from the host to scrape `kubectl logs` after hitting the traffic simulation endpoint. I would package the Python SLO calculator into a lightweight container and run it as a Kubernetes `CronJob` inside `kijani-staging` every two minutes, or wire the Bash script directly into the Jenkinsfile right after the staging smoke test so a >5% error rate automatically blocks the production approval gate.
* **Add Local Hot-Reloading with Skaffold:** Whenever I added new routes to `index.ts` (like the POST route for receipts and the traffic simulation endpoint), I had to rebuild `Dockerfile.production`, push `salyani123/kk-payments:latest` to Docker Hub, and run `kubectl rollout restart`. I would add **Skaffold** to watch my TypeScript files and sync changes directly into the local Minikube pods during development, saving full Docker Hub pushes and Jenkins runs strictly for final branch merges.
