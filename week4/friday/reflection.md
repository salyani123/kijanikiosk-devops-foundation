# Week 4 Reflection

**1. At what point during the project did you discover that two requirements conflicted? Describe the conflict and what you learned from resolving it.**
The biggest conflict I encountered was between the strict systemd hardening (specifically `ProtectSystem=strict`) and Ansible's need to deploy configuration files, as outlined in Challenge D. `ProtectSystem=strict` mounts the entire OS file system as read-only for the service. However, Ansible needs to write the `.env` file so the service can read its port and environment variables. I learned that security isn't just about locking everything down; it's about engineering precise exceptions. To resolve this, I had to ensure Ansible deployed the `.env` file to a specifically designated, writable directory (`/opt/kijanikiosk/config/`) and explicitly point the systemd `EnvironmentFile` directive to that exact path. 

**2. The hardening decisions document is written for Nia. Rewrite one sentence from it in the technical language you would use if writing it for Tendo instead. What is lost and what is gained in the translation?**
*Original sentence for Nia:* "By forcing the surrounding system to act as if it is entirely read-only, we ensure that if a bad actor takes over the application, they are trapped."
*Translated for Tendo:* "By implementing the `ProtectSystem=strict` directive in the systemd unit file, we mount the OS directory hierarchy as read-only for the service process, effectively mitigating unauthorized persistent filesystem modifications during a potential application compromise."
*What is lost and gained:* What is lost is accessibility; Nia would likely stop reading at "directive" or "mount." What is gained is engineering precision. Tendo immediately knows exactly which Linux kernel feature was used to achieve the security goal, allowing him to verify the code quickly.

**3. Looking at the full pipeline (Terraform plus Ansible plus pipeline.sh): what is the single most fragile handoff? The place most likely to break in a real production environment that differs slightly from your test setup? What would you need to know about the target environment to make that handoff robust?**
The single most fragile handoff is exactly where my pipeline originally failed: the transition between Terraform finishing the EC2 creation and Ansible attempting to connect via SSH. Terraform reports "apply complete" the millisecond the AWS API accepts the request, but the Ubuntu operating system takes time to boot and start the SSH daemon. I patched this with a hardcoded `sleep 30` in my shell script. In a real production environment with heavier AMIs or network latency, 30 seconds might not be enough, causing the pipeline to fail randomly. To make this robust, I would need to replace the hardcoded sleep with a dynamic health check, such as an Ansible `wait_for` task that actively polls port 22 on the target IPs before proceeding with the rest of the playbook.
